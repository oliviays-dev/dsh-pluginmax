## 0. 一页结论

### 0.1 平台治理是什么

平台治理是对**共享能力进入平台后产生的跨边界风险**进行持续管理：

> 谁把什么能力带入平台，平台内谁可以使用，它能访问什么、执行什么，依据哪个授权，产生了什么结果，以及平台如何暂停、回滚和追责。

平台治理的对象不是“平台上所有事情”，而是四类具有平台外溢风险的对象：

1. **共享资源**：Skill、MCP、功能面板插件、工作台方案。
2. **访问关系**：发布者资格、安装 entitlement、工作区/项目授权和业务数据权限。
3. **运行时动作**：AI Principal、Runtime Profile、Action Ticket、工具调用、写入与审批。
4. **运营证据**：版本、兼容性、审计、告警、下架、回滚和例外记录。

平台治理不是增长引擎，也不是平台性能团队。它具体做五件事：

1. **发牌照**：确认资源是谁发布的、谁负责、版本是什么。
2. **画边界**：规定谁能安装、能读取什么、能调用什么、能执行什么动作。
3. **设门禁**：高风险资源、连接和动作进入前必须有认证、授权或审批。
4. **装刹车和黑匣子**：越界时阻断，运行后留下可还原的审计证据。
5. **做事故处置**：发现风险后禁用资源、吊销票据、回滚版本和冻结发布者。

常态下治理不踩刹车；只有越界、高风险或事故时才踩刹车。业务量是否增长、页面是否快、业务结论是否正确，不由治理负责。

### 0.2 顶层目标

> **确保纳入治理范围的共享资源、授权关系和高风险动作都处在明确边界内；任何越界都能被发现、阻断、追溯和处置。**

治理目标的度量分为四类，不包含业务增长或平台性能：

1. **边界覆盖**：应受治理的资源和动作是否全部纳入。
2. **越界结果**：是否存在未经授权的数据访问、权限扩大或高风险动作。
3. **证据完整**：每次高风险动作能否还原主体、授权、动作、资源和结果。
4. **处置有效**：发现问题后能否在目标时间内停止运行、禁用资源和回滚版本。

上线后的目标不是提高业务量，而是让四类治理问题有稳定、可度量的答案：

- 平台管理员：哪些资源和高风险动作尚未纳入治理？
- 安全与审计：是否存在越权、未声明副作用或不可追溯的动作？
- 工作区/项目管理员：安装资源后是否扩大了业务数据权限？
- 业务负责人：需要治理裁决时，规则是否明确、结果是否可解释？

### 0.3 上线初期判断

上线初期应坚持：

- **受控供给**：先官方和认证资源，不开放任意开发者上传并即时执行代码。
- **权限不扩大**：安装、复制、启用的权限不能超过用户已有的业务权限。
- **执行有边界**：AI 必须通过 Runtime Profile、Action Ticket、工具策略和预算执行。
- **风险分级**：自动化校验为主，人工只处理高风险和新风险例外。
- **可观测、可处置**：资源能下架，版本能回滚，配置保留，审计可追溯。
- **责任分散但规则统一**：平台管机制，Function Owner 管业务内容，资源 Owner 管质量与响应。

### 0.4 上线 P0

正式上线前必须具备六项最小治理能力：

1. 统一资源身份：发布者、Owner、来源、版本、校验值、兼容范围可追溯。
2. 发布准入：Schema 校验、权限声明、敏感信息扫描和高风险人工审核。
3. 权限执行：工作台权限、资源权限、业务数据权限三层取交集，并在服务端二次鉴权。
4. 运行控制：AI Runtime Profile、Action Ticket、工具白名单/黑名单、预算和人工确认。
5. 运营处置：资源禁用、版本回滚、运行中止和用户配置占位保留。
6. 审计基线：发布、安装、连接、授权、执行、失败、禁用均有结构化记录。

### 0.5 明确不做

上线初期不把以下事项纳入平台治理主责：

- 业务系统自身的数据分类、保留期限和主数据质量。
- 每个 Skill 的业务结论是否正确、每个 MCP 返回数据的业务含义是否准确。
- 全员组织、岗位、汇报关系和入离职管理。
- 社区内容审核、评分、评论和开发者声誉运营。
- 付费、分成和结算体系。
- API 和业务组件的全量资源治理。
- 大型治理委员会和复杂规则引擎。
- 用户增长、留存、转化和业务运行量增长。
- 平台延迟、吞吐、可用性、容量和一般故障修复。
- 业务输出是否正确、业务收益和 ROI。

## 1. 明确定义平台治理的 Scope

### 1.1 一句话边界

> **平台治理管理共享资源进入平台后的准入、授权、运行边界和处置；不负责业务增长、平台性能或业务结果。**

平台必须保证：

- 资源可被识别和找到。
- 发布者与负责人可被追责。
- 权限来源与数据范围可解释。
- 执行过程可限制、可中止。
- 变更与异常可追溯、可回滚。

平台不直接保证：

- 业务判断一定正确。
- 业务系统内部数据一定完整。
- 每个 Agent 输出一定满足专业质量。
- 所有用户都一定会正确使用资源。

### 1.2 平台治理要回答的五个问题

| 问题 | 治理对象 | 最小证据 |
| --- | --- | --- |
| 这是谁、由谁负责？ | Principal、发布者、Owner、资源 | Principal ID、发布者 ID、Owner、版本 |
| 它能访问什么？ | 资源权限、数据范围、连接凭据 | 权限声明、数据集/API 范围、授权记录 |
| 谁允许它执行？ | 平台角色、工作区/项目授权、Action Ticket | Grant、Ticket、审批记录 |
| 它实际做了什么？ | 工具调用、数据读取、写入、外部发送 | Run、调用日志、交付物、审计事件 |
| 出问题如何停止和恢复？ | 禁用、回滚、吊销、降级、复盘 | 处置记录、影响范围、恢复结果 |

### 1.3 平台治理与相邻领域的边界

| 领域 | 主责 | 与平台治理的接口 |
| --- | --- | --- |
| 平台治理 | 资源准入、权限边界、运行控制、审计与处置 | 提供统一规则、控制面和证据链 |
| 业务治理 | 业务流程、业务规则、专业判断、结果验收 | 平台执行其授权和审批规则，不替代业务决策 |
| 数据治理 | 数据分类分级、质量、生命周期、合规范围 | 平台消费数据标签与访问策略，不维护数据主数据 |
| IT 安全 | 身份基础设施、密钥、网络、漏洞和应急体系 | 平台接入安全标准，执行应用层权限与审计 |
| 平台工程 / SRE | 延迟、吞吐、可用性、容量、一般故障和性能优化 | 治理消费风险信号并决定是否暂停资源，不承担性能指标 |
| 产品运营 | 用户增长、内容运营、社区活跃、开发者运营 | 治理提供安全边界和风险处置，不承担拉新和活跃指标 |
| 组织与 HRM | 组织、岗位、员工生命周期 | 平台只保存 Principal 与授权所需映射 |

### 1.4 In Scope：上线初期纳入

#### A. 供给治理

- Skill、MCP、功能面板插件、工作台方案的资源身份与 Owner。
- 发布者身份：官方、认证团队、私有/团队来源。
- 资源元数据、版本、来源、校验值、依赖和兼容范围。
- 资源 Schema 校验、领域查重、敏感字段扫描和安全审核。
- 资源的上架、更新、弃用、下架和例外记录。

#### B. 访问治理

- Human Principal 与 AI Principal 的显式授权。
- 平台、工作区、项目三层角色和 Grant。
- 市场可见性、安装 entitlement、工作台可见范围和复制规则。
- `工作台权限 ∩ 资源权限 ∩ 业务数据权限` 的服务端校验。
- 插件清单中的数据权限与实际 API 鉴权的一致性。

#### C. 运行治理

- AI Runtime Profile、工具 allow/deny、资源范围和预算。
- 与工作区、项目、任务、工作流实例绑定的 Action Ticket。
- 写入、外部发送、关键审批等高风险动作的人工确认。
- 运行中止、超时、失败、重试和人工接管。
- 禁用资源、吊销票据和未知版本被调用时的治理降级。

#### D. 证据与处置

- 发布、安装、启用、连接、授权、执行、失败和禁用事件。
- 版本、来源、授权来源和审批依据。
- 风险告警、下架、回滚、票据吊销和影响范围记录。
- 治理覆盖率、审核 SLA、治理逃逸、证据完整和风险止损指标。

### 1.5 Out of Scope：上线初期不纳入主责

| 不纳入事项 | 原因 | 后续接口 |
| --- | --- | --- |
| 社区自由上架与即时运行 | 同页代码缺少强隔离，风险不可控 | 先认证供给，后续建设隔离运行时 |
| 公开评分、评论和排行榜 | 低供给阶段容易制造虚假质量信号 | 有稳定供给和真实使用量后再建设 |
| 付费、分成与结算 | 不是建立信任的前置条件 | 交易前先完成责任、质量和退款规则 |
| 全平台细粒度 ABAC/策略引擎 | 初期规则数量有限，复杂引擎成本高于收益 | 规则种类增长后再抽象 |
| 全部存量资源一次清洗 | 会制造大规模迁移风险 | 只治理近期有调用记录的活跃资源 |
| 业务内容逐条审批 | 平台不可能替代 Function Owner | 业务 Owner 负责内容，平台处理高风险例外 |
| 数据内容与主数据治理 | 已有业务系统/数据治理主责 | 平台读取数据标签和权限策略 |
| 组织人事生命周期 | 应由 HRM 管理 | 平台通过 Principal Link 映射 |
| 全量 API/业务组件治理 | 资源模型和消费链路不同 | 先限定 Skill、MCP、面板、方案 |
| 业务量是否增长 | 属于产品与运营目标，治理无法直接驱动 | 治理只提供安全、可控的使用边界 |
| 页面是否够快、系统是否稳定 | 属于平台工程和 SRE | 治理只在风险超阈值时暂停资源或限制动作 |

### 1.6 Scope 的三条硬边界

1. **平台可见不等于数据可见。**
   市场可见、工作台可见、安装 entitlement 和业务数据权限必须分开建模。

2. **平台管理员不等于业务数据超级用户。**
   管理员可以下架和阻断资源，但不能因为治理身份看到全部业务数据。

3. **安装不等于执行，执行不等于完成。**
   安装只创建 entitlement；执行需要 Runtime Profile 和 Ticket；业务节点完成仍需交付物与审批门禁。

### 1.7 典型问题归责

| 典型问题 | 治理是否主责 | 主责方 | 治理做什么 |
| --- | --- | --- | --- |
| 业务量、留存或转化不增长 | 否 | 产品 / 运营 / 业务 | 不做业务增长目标，只报告治理是否造成明确阻塞 |
| 页面慢、吞吐低、可用性差 | 否 | 平台工程 / SRE | 使用风险和运行信号决定是否暂停资源，不承担性能优化 |
| 业务报告结论错误 | 否 | Function Owner / 资源 Owner | 确保权限和工具边界，不判断业务结论 |
| 插件存在漏洞并导致故障 | 部分 | 研发负责修复，安全负责漏洞标准 | 认证准入、版本拦截、禁用、回滚和审计 |
| MCP 能读取未授权数据 | 是 | 平台治理 / 安全 | 阻断连接、限制数据范围、吊销凭据和票据 |
| AI 无有效 Ticket 执行写入 | 是 | 平台治理 / 运行控制 | 拒绝执行、记录事件、修复策略 |
| 资源没有 Owner 或版本不可追溯 | 是 | 平台治理 | 阻断发布和下架无主资源 |
| 用户安装后获得了额外业务权限 | 是 | 平台治理 / 业务 API Owner | 服务端二次鉴权、修复授权计算 |
| 权限说明不清楚、安装前未提示 | 是 | 平台治理 / 产品 | 修正披露规则和安装确认 |
| 审批流程慢且由治理规则造成 | 是 | 平台治理 | 优化自动校验、SLA 和例外流程 |
| 工作台复制失败 | 否 | 对应产品模块 / 前端 | 不使用成功率作为治理北极星 |

## 2. 顶层目标与阶段目标

### 2.1 顶层目标

> **确保纳入治理范围的共享资源、授权关系和高风险动作都处在明确边界内；任何越界都能被发现、阻断、追溯和处置。**

治理是控制职能，不是增长职能。它可以阻止不安全的能力上线，但不能决定用户是否愿意使用、平台能承载多少业务量，也不能解决页面慢和系统吞吐问题。

#### 2.1.1 一级治理结果

| 结果 | 具体含义 | 上线目标 |
| --- | --- | --- |
| 没有黑资源 | 所有在平台中可发现或可执行的资源都有身份、Owner、版本和认证 | 覆盖率 100% |
| 没有黑授权 | 所有高风险动作都有 Principal、Grant、Profile 和 Ticket | 覆盖率 100% |
| 没有越界逃逸 | 不存在未声明的数据访问、权限扩大或高风险动作 | 已确认逃逸数 0 |
| 可以还原 | 可还原谁发起、谁授权、执行了什么、使用哪个资源版本 | 证据完整率 100% |
| 可以停住 | 发现风险后可以停止运行、禁用资源、吊销票据、回滚版本 | 达到 P95 时限 |
| 规则可预期 | 同类问题得到同类判断，例外有责任人、期限和补偿措施 | SLA 与例外合规率达标 |

#### 2.1.2 可计算口径

```text
治理覆盖率 =
  已被纳入治理的资源或高风险动作
  / 应纳入治理的资源或高风险动作

治理逃逸率 =
  经审计抽检或事件确认的越权、未声明副作用或证据缺失对象
  / 审计抽检覆盖的治理对象

证据完整率 =
  具备 Principal、Grant、Profile、Ticket、资源版本和审计事件
  的高风险动作
  / 全部应审计的高风险动作

运行阻断 P95 =
  风险发现 -> Run 停止生效的 P95 时长

资源禁用 P95 =
  风险发现 -> 资源不可安装/不可启用/不可调用的 P95 时长

回滚恢复 P95 =
  风险发现 -> 版本回滚或安全降级生效的 P95 时长

例外合规率 =
  有审批、责任人、补偿措施和到期时间的例外
  / 全部治理例外
```

治理逃逸必须同时来自两条发现路径：

1. 已发生的安全、权限或审计事件。
2. 按风险分层的主动抽检。

只统计“没有事故”不能证明没有逃逸，因为可能没有发现。

#### 2.1.3 不使用增长型北极星

治理不设置 DAU、业务运行量、资源安装量、转化率或营收类北极星。原因是：

- 这些结果由产品、运营和业务场景共同决定。
- 治理不能直接创造使用需求。
- 用业务量评价治理，会诱发放水和形式化扩张。
- 用审批数量评价治理，会诱发无效流程。

治理的一级结论使用“覆盖率 + 已确认逃逸 + 证据完整 + 止损时限”四项硬结果，不合成加权总分。

### 2.2 治理目标与非目标

| 治理目标 | 不接受的替代指标 |
| --- | --- |
| 应治理资源和动作 100% 纳管 | 资源发布数量、安装次数、Agent 调用量 |
| 已确认越权、未声明副作用和权限扩大为 0 | 审批数量、工单关闭量 |
| 高风险动作证据完整且可还原 | 日志条数、审计页面访问量 |
| 风险发现后能在时限内停止和回滚 | 平台平均延迟、吞吐、可用性 |
| 同类问题的判断规则稳定、可解释 | 规则数量、审批节点数量 |
| 例外有期限、有补偿措施且可撤销 | 例外审批通过率 |

### 2.3 上线成功标准

正式上线时，治理侧应能验收以下事项：

1. 应纳入治理的 Skill、MCP、功能面板插件和工作台方案覆盖率 100%。
2. 可执行资源认证率 100%，资源 Owner、版本和来源完整率 100%。
3. 核心业务 API 的服务端二次鉴权覆盖率 100%。
4. 高风险动作的 Principal、Grant、Profile 和 Ticket 覆盖率 100%。
5. 未经确认或正式自动批准的高风险动作为 0。
6. 经事件和抽检确认的未授权访问、权限扩大和未声明副作用为 0。
7. 高风险动作的证据完整率和审计还原通过率均为 100%。
8. 治理例外审批、责任人和到期时间完整率 100%。
9. Run 停止 P95 ≤ 5 分钟，资源禁用 P95 ≤ 30 分钟，回滚恢复 P95 ≤ 60 分钟。
10. 治理规则承诺的审核 SLA 达成率 ≥ 95%。

以下指标由其他团队负责，不作为治理上线验收：

- 页面加载时长、吞吐、可用性和容量。
- 业务量、活跃、留存、转化和收入。
- 业务输出准确率和业务收益。
- 整体平台故障 MTTR。

## 3. 解决谁的问题

### 3.1 利益相关方与核心诉求

| 角色 | 核心问题 | 平台治理应提供 |
| --- | --- | --- |
| 企业管理者 / 业务一号位 | 凭什么敢把关键工作交给平台和 AI？ | 明确边界、人工决策、可审计、可止损 |
| CIO / 安全 / 风险 | 第三方代码、MCP 连接和 AI 会不会越权？ | 受控供给、最小权限、凭据托管、审计 |
| 审计 / 内控 | 能否解释一次 AI 行动的责任链？ | Principal、Grant、Ticket、Run、审批和交付物证据 |
| 平台管理员 | 平台上有哪些能力在运行，谁负责？ | 资源目录、Owner、版本、风险状态、禁用和下架 |
| 业务 Function Owner | 平台是否会把业务内容审批全部压给我？ | 责任清晰、规则统一、只处理专业判断和高风险例外 |
| 资源 Owner / 开发者 | 发布规则是否可预测，审核是否会成为瓶颈？ | 自动校验、明确 SLA、可解释退回和例外通道 |
| 工作区 / 项目管理员 | 成员安装资源后会不会扩大数据权限？ | 三层权限取交集、安装确认、范围和票据控制 |
| 终端用户 | 我能看到什么，是否会被 AI 偷偷操作？ | 权限说明、人工确认、可撤销和明确失败反馈 |
| 平台运营 / 客服 | 出问题后如何快速定位和恢复？ | 版本、错误码、影响范围、回滚和下架操作 |

### 3.2 核心矛盾

上线初期存在三组必须平衡的矛盾：

1. **信任与速度**：审核过重会拖慢供给，审核过轻会带来安全和质量风险。
2. **统一与自治**：平台需要统一规则，业务 Function 需要保留专业判断权。
3. **能力扩张与可解释性**：新增资源越快，权限、数据和责任链越难解释。

治理方案必须明确取舍：

- 首期宁可供给少，也不开放不可信代码。
- 首期宁可入口集中，也不让同一风险由多个团队重复判断。
- 首期优先保证可退出，再追求自动化更新和生态规模。
- 首期用有限规则覆盖高风险场景，不建设“大而全”的治理平台。

## 4. 阶段目标

> 以下阶段以能力成熟度和退出条件划分，不以自然月代替验收。

### 4.1 阶段 A：可信上线

**阶段定位**：完成最小信任闭环，允许平台正式开放使用。

**主要解决**

- 管理者、安全和审计不敢上线的信任问题。
- 平台无法回答“有哪些资源在运行、谁能用、出了事怎么办”。
- AI 执行缺少身份、权限、预算和审计基线。

**阶段范围**

- 官方认证资源 + 私有资源。
- 认证功能面板插件，由平台/profile 预先装配。
- 工作台方案复制制，不允许自动覆盖用户实例。
- Skill 受控发布；MCP 首期优先只读连接。
- AI Runtime Profile、Action Ticket、预算和审计基线。
- 资源禁用、版本回滚、票据吊销和最小治理控制台。

**退出条件**

- P0 治理能力全部通过验收。
- 所有可执行资源完成安全审查和兼容性登记。
- 三层权限、服务端二次鉴权、敏感配置扫描通过测试。
- 完成至少一次“异常插件下架 + 用户配置保留”演练。
- 完成至少一次“AI 越权请求拒绝 + Ticket 吊销”演练。
- 关键审计事件可关联到 Principal、Grant、Ticket、Run 和资源版本。

### 4.2 阶段 B：运营化

**阶段定位**：从“可以上线”进入“可以持续运营”。

**主要解决**

- 平台治理仍依赖少数人经验，规则和处置不可复制。
- 资源 Owner 不清楚责任，问题发生后响应不稳定。
- 用户对权限和资源质量的理解不足，投诉与误用增加。

**阶段范围**

- 治理工作台：资源清单、发布状态、认证状态、运行状态、风险和处置。
- 发布审核 SLA、例外审批和到期复审。
- 治理风险信号：未知版本、禁用资源仍被调用、权限拒绝和异常调用。
- 资源 Owner 响应机制和版本弃用流程。
- 团队私有市场或指定工作区可见范围的最小能力。
- 认证团队资源试点，但仍受平台安全门禁。

**退出条件**

- 90% 以上的常规发布由自动校验完成，人工只处理高风险例外。
- 所有已发布资源有明确 Owner、支持入口和版本责任。
- 高优先级治理事件有明确响应时限和复盘记录。
- 连续一个治理周期无“未声明权限扩大”或“资源绕过服务端鉴权”问题。
- 资源平均审核周期、退回原因和例外到期情况可量化。

### 4.3 阶段 C：可复制

**阶段定位**：从“平台团队集中治理”升级为“在统一规则下分权治理”。

**主要解决**

- 业务部门希望维护自己的资源和私有市场，但平台团队成为瓶颈。
- 认证发布者数量增加后，人工审核无法随供给线性扩展。
- 资源更新、依赖兼容和跨工作区复用需要标准化。

**阶段范围**

- 认证发布者体系与分级权限。
- 团队市场、版本更新提示、兼容检查和选择性合并。
- 自动安全扫描、依赖审计、质量信号和定期复审。
- 分级事件响应、发布者停权和资源批量处置。
- 明确社区开放的前置隔离条件。

**退出条件**

- 认证发布者可在规则内自助发布，不需要逐条平台人工审批。
- 高风险资源仍必须通过安全认证，低风险元数据变更可自动发布。
- 资源更新和回滚不会影响用户已保存实例。
- 认证发布者增长时，治理覆盖率、确认逃逸数和止损时限不退化。
- 社区/第三方运行隔离方案完成安全评审后，才进入下一阶段。

## 5. 治理原则

### 5.1 风险分级，不做平均用力

按资源类型、动作副作用和数据敏感度分级：

- 只读、元数据、布局类变更：自动校验后可发布。
- 可执行 UI 插件：必须代码审核、依赖检查和兼容验证。
- 写入 MCP、外部发送、权限提升：必须人工审批和运行票据。
- 不可信第三方代码：上线初期不运行。

### 5.2 自动化优先，人工处理例外

可以自动判断的内容不应进入人工审批：

- Schema 是否合法。
- ID、版本、来源和校验值是否完整。
- 文档字段是否缺失。
- 同领域资源是否高风险重复。
- 是否存在明文密钥或敏感配置。
- 宿主版本是否兼容。

需要人工判断的例外：

- 高风险重复但业务确需独立保留。
- MCP 写入副作用无法明确分级。
- 新类型资源尚无安全基线。
- 自动化误判且影响业务上线。

### 5.3 最小权限与显式授权

- Principal、资源、工作区、项目角色均显式授权。
- Persona、Owner、岗位名称和安装动作不授予业务权限。
- AI 不得继承人类 Bearer Token。
- 工具调用每次重新鉴权，deny 优先。
- 凭据只由平台托管，资源文档和工作台配置不得保存明文密钥。

### 5.4 供给责任与平台责任分离

- 平台负责统一规则、控制点、审计和处置。
- 业务 Function 负责资源适用性、专业边界和支持渠道。
- 资源 Owner 负责内容质量、版本更新和问题响应。
- 安全团队负责可执行代码与高风险连接的安全基线。
- 审计负责证据完整性和抽检，不替代日常审批。

### 5.5 可退出优先于可扩张

任何新能力上线前必须先回答：

- 如何禁用？
- 如何回滚？
- 用户数据是否保留？
- 运行中的任务如何处理？
- 已安装用户如何提示和降级？

无法停用或回滚的资源不应进入正式市场。

### 5.6 状态分离，不混淆语义

资源至少区分三种状态：

| 状态维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| 目录生命周期 | 资源是否仍在目录中维护？ | draft / published / deprecated |
| 安全认证 | 是否经过允许的风险审核？ | unreviewed / certified / revoked |
| 运行可用性 | 当前是否允许被启用和运行？ | enabled / suspended / disabled |

不能用“已发布”同时表示业务可发现、安全已认证和运行已开放。

## 6. 治理总体布局

### 6.1 逻辑架构

```text
┌─────────────────────────────────────────────────────────────┐
│                       治理运营层                            │
│ 资源清单 / 风险队列 / 例外审批 / 事件处置 / 指标与复盘       │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│                       证据与审计层                          │
│ Principal / Grant / Ticket / Run / 版本 / 调用 / 审批        │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│                       运行控制层                            │
│ Runtime Profile / Tool Policy / Budget / Approval / Abort   │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│                       访问控制层                            │
│ 平台角色 / 工作区与项目 Grant / Entitlement / 数据权限       │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│                       供给治理层                            │
│ Resource Registry / Manifest / Publisher / Version / Review │
└─────────────────────────────────────────────────────────────┘
```

这些是**逻辑能力**，不要求首期建设五个独立服务。可以在现有插件、存储域和管理页面内逐步实现。

### 6.2 五类治理平面

| 平面 | 核心能力 | 首期产物 |
| --- | --- | --- |
| 供给治理 | 资源身份、准入、版本和认证 | 统一资源清单与发布门禁 |
| 访问治理 | Principal、Grant、entitlement 和三层权限 | 服务端鉴权与权限说明 |
| 运行治理 | Runtime Profile、Ticket、工具、预算、审批 | 可控的 Agent 执行链路 |
| 证据治理 | 审计、版本、运行和处置记录 | 可还原的证据链 |
| 运营治理 | 风险队列、例外、事件、复盘和指标 | 最小治理运营台 |

### 6.3 当前基础与需要补齐的能力

从现有设计材料看，可复用的基础包括：

- Principal 统一授权主体。
- 工作台、业务数据和插件三层权限思路。
- 市场资源版本快照与复制制。
- Runtime Profile、Action Ticket、工具策略和预算。
- 插件禁用/未知版本占位和审计事件设计。

需要重点补齐：

- 跨 Skill、MCP、面板和方案的统一资源清单。
- 发布者身份、认证状态和发布责任。
- 可执行资源的正式安全审核流程。
- MCP 连接的 provider 治理与写入副作用分级。
- 统一的策略判断、禁用、回滚和事件处置能力。
- 面向平台运营的治理视图和可量化指标。

## 7. 治理对象与生命周期

### 7.1 核心对象

| 对象 | 定义 | 关键字段 |
| --- | --- | --- |
| Principal | 可授权、可追责主体 | id、kind、status、source |
| Publisher | 资源发布主体 | publisherId、等级、认证状态、责任人 |
| Resource | 可被发现和使用的共享能力 | resourceId、类型、Owner、版本、来源、状态 |
| Entitlement | 用户或工作区被允许使用资源 | principalId、resourceId、scope、有效期 |
| Runtime Profile | AI 的执行方式与资源限额 | 模型、工具策略、预算、并发、超时 |
| Action Ticket | 特定上下文内的执行授权 | principalId、contextId、允许动作、有效期 |
| Run | 一次实际执行 | runId、ticketId、输入、输出、状态、错误 |
| Audit Event | 对关键动作的不可变证据 | 操作者、对象、动作、结果、前后值、时间 |

### 7.2 资源发布生命周期

```text
草稿
  -> Schema/元数据校验
  -> 领域查重与敏感扫描
  -> 风险分级
      -> 低风险：自动认证
      -> 高风险：安全/业务审核
  -> 认证通过
  -> 发布到指定市场范围
  -> 安装/复制
  -> 更新或弃用
  -> 暂停/下架
  -> 修复后重新认证或永久废弃
```

任何状态变化都记录：

- 操作者与发布者。
- 资源 ID 与版本。
- 变更前后值。
- 审核或例外依据。
- 生效范围和生效时间。

### 7.3 功能面板插件准入流程

```text
插件包提交
  -> 清单完整性与版本校验
  -> 发布者身份验证
  -> 依赖与供应链检查
  -> 数据权限和外部调用检查
  -> 同页代码安全审核
  -> 宿主兼容性测试
  -> 禁用、停止和恢复路径验证
  -> 认证并预装配
  -> 用户 entitlement
  -> 工作台实例引用
```

硬约束：

- 首期不执行市场返回的任意字符串代码、HTML 或脚本。
- 用户侧“安装”只创建 entitlement，不下载并即时执行未知 bundle。
- 新版本必须重新做兼容与安全校验。
- 下架插件时显示只读占位，不删除用户布局引用。

### 7.4 Skill 准入流程

重点检查：

- 展示名、描述、主业务领域和 Owner。
- 适用场景、输入输出、限制和不适用边界。
- 是否有明确支持渠道和使用文档。
- 是否要求超出资源类型的权限或携带密钥。
- 是否包含诱导越权、绕过审批或泄露数据的指令。
- 是否与同领域资源高度重复。

Skill 本身不承载工具权限和凭据。需要外部能力时，通过受治理的 MCP 或平台工具访问。

### 7.5 MCP 准入流程

重点检查：

- 服务身份、鉴权和凭据托管方式。
- 数据范围、租户/工作区隔离和调用方隔离。
- Tool 清单及每个 Tool 的读写副作用。
- 写入、删除、审批、发送等高风险动作。
- 超时、限流、错误码、断开和恢复策略。
- 调用日志是否足以还原一次业务动作。

建议首期采用：

- 官方/认证 MCP。
- 只读优先。
- 写入类 Tool 必须逐项标识副作用，并配置 Ticket 与人工确认。
- 未接入正式治理 provider 时，不显示“已连接”等伪状态。

### 7.6 工作台方案准入流程

- 预览只包含布局和默认配置，不包含真实业务数据。
- 复制时检查必需插件、权限和兼容性。
- 不复制原 Owner 的私有筛选值、项目 ID 和敏感配置。
- 复制后生成独立实例，市场更新不自动覆盖。
- 团队共享方案发布前执行敏感字段扫描。
- 方案可见范围不改变任何业务对象 ACL。

### 7.7 AI 运行生命周期

```text
AI Principal active
  AND Companion active
  AND 目标范围有有效 Grant
  AND Runtime Profile active
  AND Action Ticket 有效
  AND 当前工具与资源在允许范围内
  -> 执行
  -> 记录 Run 与调用证据
  -> 产出交付物
  -> 人工/自动门禁
  -> 完成、失败、超时或中止
```

| 场景 | 默认策略 |
| --- | --- |
| 读取已授权业务数据 | 自动执行并记录 |
| 生成文件或报告 | 自动执行，进入交付物门禁 |
| 写入业务系统 | 默认人工确认 |
| 对外发送、发布或承诺 | 必须人工确认 |
| 修改权限、扩大数据范围 | 管理员审批并记录前后值 |
| 超出预算或跨上下文复用 Ticket | 拒绝执行 |

### 7.8 紧急处置流程

| 级别 | 示例 | 动作 | 目标 |
| --- | --- | --- | --- |
| S1 | 数据泄露、破坏性写入、越权访问 | 立即禁用资源、吊销 Ticket、冻结发布者、保存证据 | 先止损，后定位 |
| S2 | 认证失效、严重权限配置错误、已禁用版本仍可运行 | 隐藏插件、吊销票据、回滚版本、保留用户配置 | 限制影响范围 |
| S3 | 元数据缺失、文档错误、分类冲突 | 退回修复、限时更正、必要时隐藏条目 | 不中断现有运行 |

原则：

- 下架不等于删除历史证据。
- 目录治理不自动中断既有调用，除非存在安全或合规风险。
- 紧急处置必须通知资源 Owner 和受影响范围负责人。
- S1/S2 事件必须完成复盘并形成规则或产品改进项。

## 8. 能力地图与建设优先级

### 8.1 优先级定义

| 优先级 | 定义 | 判断标准 |
| --- | --- | --- |
| P0 | 上线阻断项 | 缺失则无法证明权限、运行、审计或止损成立 |
| P1 | 运营必需项 | 不阻断首发，但供给增长后会造成人工瓶颈 |
| P2 | 规模化项 | 认证团队和资源量增长后再建设 |
| 暂缓 | 无明确消费者 | 没有页面、接口、规则或运营流程消费 |

### 8.3 建设顺序

不建议按页面优先建设，而应按控制链顺序建设：

```text
统一对象与 ID
  -> 资源清单与状态
  -> 权限与运行约束
  -> 发布与审核门禁
  -> 审计与处置
  -> 运营视图与指标
  -> 认证发布者与自动化
```

顺序原因：

- 没有统一对象，无法建控制台。
- 没有权限和执行控制，审核通过也无法保证安全。
- 没有审计与处置，市场规模越大风险越高。
- 没有运营指标，无法优化审核效率和治理成本。

## 9. P0 上线建设方案

### 9.1 Workstream 1：供给准入

**目标**：确保平台上每个可发现、可执行的资源都能被识别、解释和追责。

**交付物**

1. 四类资源统一 Manifest。
2. 资源 ID、发布者、Owner、版本、来源、校验值和兼容范围。
3. 官方/认证/私有来源标识。
4. Schema、必填字段和状态校验。
5. 敏感信息和明文密钥扫描。
6. 可执行插件安全审核记录。
7. Skill 文档与使用边界检查。
8. MCP Tool 清单与副作用声明。

**验收**

- 缺少 Owner、版本、来源或权限说明的资源不能发布。
- 未认证的功能面板插件不能进入用户可启用状态。
- 高风险 MCP Tool 未声明副作用时不能发布。
- 所有退回都能给出可执行的修复原因。

### 9.2 Workstream 2：访问与权限

**目标**：确保可见、安装、启用和运行都不会扩大用户原有权限。

**交付物**

1. 工作台、资源、业务数据三层权限计算。
2. 安装确认与权限说明。
3. 市场可见范围与 entitlement 分离。
4. 工作台复制敏感配置隔离。
5. 服务端逐请求鉴权。
6. 管理员治理权限与业务数据权限隔离。

**验收**

- 无业务数据权限的用户无法通过面板或 MCP 获取数据。
- 复制共享工作台不携带原 Owner 的私有项目和筛选值。
- 插件清单超范围请求时，服务端明确拒绝。
- 治理管理员无法因管理员身份查看未授权业务对象内容。

### 9.3 Workstream 3：运行控制

**目标**：确保 AI 和外部连接只在明确上下文、权限和预算内执行。

**交付物**

1. AI Principal、AI Companion、Runtime Profile 绑定。
2. 工具 allow/deny 与资源范围。
3. Action Ticket 上下文、有效范围和过期。
4. 预算、并发、超时和最大运行次数。
5. 写入、外部发送和关键审批的人工确认。
6. Run、Ticket、Grant 和审计事件关联。
7. 运行中止与票据吊销。

**验收**

- 未配置 Runtime Profile 的 AI Principal 不能派发。
- Ticket 不能跨工作区或跨流程实例复用。
- 预算或时限耗尽时停止执行并显式反馈。
- 高风险动作不能绕过人工确认。

### 9.4 Workstream 4：运营与止损

**目标**：资源出现质量、安全或兼容问题时，平台能快速限制影响并恢复。

**交付物**

1. 资源状态查询和 Owner 信息。
2. 禁用、下架、恢复和版本回滚操作。
3. 禁用资源只读占位。
4. 失败码和安全摘要。
5. 审计事件查询。
6. S1/S2/S3 事件分级与处置手册。
7. 最小治理指标。

**验收**

- 禁用插件后用户布局保留，重新启用后可恢复。
- 已禁用资源不能被新安装或新运行，未知版本调用进入风险队列。
- Ticket 吊销后相关运行立即失去执行权限。
- S1 问题可立即阻断运行并吊销相关票据。
- 审计记录不包含 token、完整配置和凭据。

### 9.5 Workstream 5：治理责任与流程

**目标**：明确谁对资源准入、业务适用范围、安全风险和治理处置负责。

**交付物**

1. 资源 Owner 命名规则。
2. 发布、审核、例外和复审流程。
3. 高风险动作审批矩阵。
4. 事件响应责任人和升级路径。
5. 资源下架、恢复和长期废弃规则。
6. 治理评审节奏与输入输出。

**验收**

- 每个已发布资源都有唯一 Owner 和可解析支持渠道。
- 每次人工例外都有责任人、理由、补偿措施和到期日。
- S1/S2 事件能定位到平台责任人、资源 Owner 和业务通知人。

## 10. 治理运营机制

### 10.1 决策权

> R = 负责执行，A = 最终负责，C = 必须咨询，I = 需要知会。

| 事项 | 平台治理负责人 | 安全/架构 | Function Owner | 资源 Owner | 工作区/项目管理员 | 审计 |
| --- | --- | --- | --- | --- | --- | --- |
| 资源基础 Schema 与平台规则 | A/R | C | C | I | I | C |
| Skill 业务适用性 | C | I | A | R | I | I |
| MCP 连接和写入副作用 | C | A | C | R | I | C |
| 可执行插件安全认证 | C | A/R | I | C | I | I |
| 官方资源发布 | A | C | C | R | I | I |
| 工作区资源和数据授权 | I | C | C | I | A/R | I |
| AI Runtime Profile 和 Ticket 基线 | A | C | C | R | I | C |
| 高风险动作审批矩阵 | A | C | C | I | C | C |
| 紧急下架和运行阻断 | A/R | C | I | I | I | C |
| 例外审批和到期复审 | A | C | C | R | I | C |
| 审计抽检 | C | C | I | I | I | A/R |

### 10.2 最小治理组织

首期不建设大型委员会，采用“一个明确负责人 + 虚拟评审小组”：

- **平台治理负责人**：对规则、准入、例外和处置结果负责。
- **平台安全/架构评审人**：负责可执行插件、MCP 和高风险动作安全基线。
- **Function Owner**：负责资源分类、适用场景和业务边界。
- **资源 Owner**：负责具体资源质量、版本和问题响应。
- **审计联络人**：负责证据要求、抽检和问题复盘。

### 10.3 评审节奏

| 节奏 | 输入 | 输出 |
| --- | --- | --- |
| 每次发布 | Manifest、审核结果、风险等级 | 通过、退回、例外或拒绝 |
| 每周 | 新增例外、异常运行、用户反馈、失败资源 | 处置项、规则修正和 Owner 跟进 |
| 每月 | 资源覆盖率、治理逃逸、证据完整、止损时限、权限拒绝 | 治理缺口和规则修正 |
| 每季度 | 资源组合、低使用资源、风险变化和路线图 | 资源保留、弃用和能力建设决定 |

### 10.4 例外管理

允许例外，但必须同时具备：

- 明确业务理由。
- 风险影响和受影响范围。
- 补偿性控制措施。
- 唯一责任人和到期时间。
- 复审计划。
- 可撤销能力。

不允许的例外：

- 可执行代码未经安全审核。
- 资源隐瞒数据权限或工具副作用。
- AI 绕过 Ticket、审批或预算。
- 以“业务紧急”为由永久扩大权限。

## 11. 指标与验收

### 11.1 治理主指标

> **应治理对象覆盖率 100%，且经事件和抽检确认的治理逃逸为 0。**

治理是控制职能，不设置业务量、DAU、转化、调用量或资源发布量类北极星。也不把覆盖率、安全、效率、体验加权成一个综合分，避免高风险项被规模指标抵消。

一级结果只包含四组：

1. **覆盖**：应治理的资源和动作全部纳管。
2. **逃逸**：确认不存在未授权访问、权限扩大、未声明副作用和证据缺失。
3. **追溯**：高风险动作可完整还原责任链和动作链。
4. **止损**：发现问题后能够在目标时间内停止、禁用和恢复。

审核周期、例外数量和治理工时是治理自身的服务约束，不作为业务价值指标。

### 11.2 上线阶段指标

| 维度 | 指标 | 计算口径 | 上线目标 |
| --- | --- | --- | --- |
| 覆盖 | 应治理资源覆盖率 | 已纳管资源 / 应纳管资源 | 100% |
| 覆盖 | 高风险动作治理覆盖率 | 具备 Principal、Grant、Profile、Ticket 的动作 / 应治理高风险动作 | 100% |
| 覆盖 | 可执行资源认证率 | 已认证可执行资源 / 已发布可执行资源 | 100% |
| 覆盖 | 资源身份完整率 | Owner、版本、来源和权限说明齐全的资源 / 已发布资源 | 100% |
| 风险 | 已确认未授权数据访问 | 经事件或抽检确认的次数 | 0 |
| 风险 | 已确认未声明权限扩大 | 经事件或抽检确认的次数 | 0 |
| 风险 | 静默高风险动作 | 未经人工确认或正式自动批准的动作数 | 0 |
| 风险 | 治理逃逸率 | 确认逃逸对象 / 审计抽检对象 | 0% |
| 风险 | 过期例外 | 超过到期时间仍未关闭或复审的例外数 | 0 |
| 证据 | 高风险动作证据完整率 | 六类治理证据完整的动作 / 全部应审计高风险动作 | 100% |
| 证据 | 审计还原通过率 | 可完整还原的抽检样本 / 抽检样本 | 100% |
| 证据 | 审计还原时长 P95 | 开始还原 -> 形成完整责任链和动作链 | ≤ 10 分钟 |
| 止损 | Run 停止 P95 | 风险发现 -> 运行停止生效 | ≤ 5 分钟 |
| 止损 | 资源禁用 P95 | 风险发现 -> 不可安装、不可启用、不可调用 | ≤ 30 分钟 |
| 止损 | 票据吊销 P95 | 风险发现 -> Ticket 失效 | ≤ 5 分钟 |
| 止损 | 回滚恢复 P95 | 风险发现 -> 版本回滚或安全降级生效 | ≤ 60 分钟 |
| 规则 | 治理审核 SLA 达成率 | SLA 内完成的治理决策 / 全部治理决策 | ≥ 95% |
| 规则 | 例外合规率 | 有审批、责任人、补偿控制和到期时间的例外 / 全部例外 | 100% |
| 规则 | 同类决策一致率 | 抽检中按同一规则得到一致结论的案例 / 抽检案例 | ≥ 95% |

### 11.3 过程信号

过程信号用于发现治理缺口，不作为业务成功指标：

| 信号 | 用途 |
| --- | --- |
| 未登记或未知版本资源调用数 | 发现“黑资源”和版本漂移 |
| 禁用资源仍被调用次数 | 验证禁用是否真正生效 |
| 权限拒绝次数与趋势 | 发现越权尝试、错误配置或策略过严 |
| 新资源审核时长 P50/P95 | 发现治理流程瓶颈 |
| 自动校验通过率和退回原因 | 判断规则是否清晰、是否制造无效工作 |
| 例外数量、年龄和到期未关闭数 | 发现规则缺口和临时授权长期化 |
| 审计抽检覆盖率和风险分层分布 | 判断“零逃逸”是否有证据支撑 |
| 策略变更数量和审计覆盖率 | 判断规则是否被随意修改 |

### 11.4 不归治理负责的指标

| 指标类别 | 示例 | 主责方 |
| --- | --- | --- |
| 业务增长 | DAU、留存、转化、收入、业务运行量 | 产品、运营和业务负责人 |
| 平台性能 | 页面延迟、吞吐、可用性、容量、错误率 | 平台工程、SRE |
| 一般故障 | 平台整体 MTTR、故障率、发布回滚率 | 平台工程、SRE |
| 业务质量 | 报告准确率、建议采纳率、业务收益、ROI | Function Owner、资源 Owner |
| 产品体验 | 页面易用性、复制成功率、安装转化率 | 对应产品团队 |

治理只提供两类接口：

- 消费安全、权限、风险和运行证据，决定是否阻断或暂停。
- 向产品、SRE 和业务团队提供治理摩擦与风险信号，由主责方优化。

### 11.5 反指标

以下指标不能单独作为治理成功标准：

- 发布资源数量。
- 审核通过数量。
- 审批节点数量。
- 禁用资源数量。
- 工单关闭数量。
- Agent 调用次数。
- 业务运行量增长。
- 系统延迟或吞吐。
- 零事故本身。

“零事故”不能单独使用，因为它可能来自未发现、未上报或业务不敢使用。应与治理覆盖率、抽检逃逸率、证据完整率和止损能力一起判断。

### 11.6 指标治理

| 指标 | 数据源 | 负责人 | 复盘节奏 | 触发动作 |
| --- | --- | --- | --- | --- |
| 应治理资源覆盖率 | 资源台账、插件装配清单、市场目录 | 平台治理负责人 | 每周 | 出现黑资源则阻断发布或启用 |
| 高风险动作治理覆盖率 | Principal、Grant、Profile、Ticket、Run | 平台治理 + 安全 | 每周 | 缺失则拒绝高风险动作 |
| 治理逃逸率 | 事件、权限拒绝、审计抽检 | 审计联络人 | 每月 | 大于 0 则复盘规则和实现缺陷 |
| 证据完整率与还原时长 | Run、资源版本、审批、审计事件 | 平台治理 + 审计 | 每周 | 不达标则修复证据链并停止高风险场景 |
| 止损/恢复时长 | 告警、禁用、票据吊销、回滚记录 | 平台治理负责人 | 每次事件 + 月度 | 超时则升级事件并演练 |
| 治理 SLA 与例外合规 | 发布流程、例外台账 | 平台治理负责人 | 每周 | 超 SLA 或例外逾期则优化流程或收回授权 |

## 12. 上线路线图

### 12.1 依赖顺序

```text
Step 1：冻结治理对象、状态和责任
  -> Step 2：统一资源清单和 Manifest
  -> Step 3：完成三层权限与运行约束
  -> Step 4：建立发布、认证与例外门禁
  -> Step 5：补齐审计、禁用和回滚
  -> Step 6：最小治理控制台和指标
  -> Step 7：认证团队和私有市场试点
```

### 12.2 阶段交付

| 阶段 | 主要交付 | 不进入本阶段 |
| --- | --- | --- |
| GA 前 | 受控供给、三层权限、运行 Ticket、预算、审计、禁用、回滚、最小控制台 | 社区开放、自由上传、复杂策略引擎、付费 |
| GA 后 0-90 天 | 风险分级、SLA、治理风险信号、团队私有市场试点、认证团队小范围发布 | 大规模第三方生态、评分体系 |
| GA 后 90-180 天 | 认证发布者分级、自动扫描、选择性更新、批量处置、治理规则优化 | 不可信代码社区市场，除非隔离运行时达标 |

### 12.3 优先级变更规则

任何能力进入 P0，必须满足至少一个条件：

- 缺少它会产生不可接受的权限、数据或安全风险。
- 缺少它无法完成上线验收或事故止损。
- 缺少它会阻断核心用户闭环。

任何能力进入 P1/P2，必须说明：

- 消费者是谁。
- 当前人工替代方案是什么。
- 不建设会造成什么可量化损失。
- 何时重新评估优先级。

## 13. 主要风险与应对

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 把所有问题都归为平台治理 | scope 膨胀、组织抵触、上线延迟 | 坚持“准入、授权、运行边界和处置”定义，增长、性能和业务结果归还主责方 |
| 中央平台逐条审批 | 供给瓶颈、开发体验差 | 自动校验为主，例外人工；高风险才进入安全审核 |
| 认证标识失真 | 用户误信低质量资源 | 认证状态可撤销、定期复审，认证只代表最低基线不代表业务结果正确 |
| 权限说明不等于权限控制 | 数据泄露 | 安装后每个请求仍执行服务端鉴权，三层权限取交集 |
| 同页执行第三方插件 | 可访问页面环境或越权 | 首期只运行预装配认证插件，不开放任意远程 JS |
| MCP 凭据分散 | 泄露和不可追责 | 平台托管凭据，资源文档和配置不得保存明文 |
| Ticket 长期化 | 一次授权覆盖过多动作 | 绑定上下文、动作、范围和有效期，禁止跨实例复用 |
| 只建设控制台，不建设控制能力 | “看得见但停不住” | 先验收禁用、回滚、吊销和执行拒绝，再完善可视化 |
| 指标追求审批数量或业务量 | 治理形式主义或 scope 越界 | 以覆盖率、确认逃逸、证据完整、止损和规则 SLA 衡量 |
| 资源下架破坏用户工作台 | 用户数据损失 | 采用只读占位、版本回滚和配置保留 |

## 14. 需要确认的决策

以下决策会直接影响上线 scope 和工期，应在方案评审时确认：

1. 首发市场是否只允许官方与认证资源？
   建议：是。

2. 功能面板插件是否只允许平台预先装配的认证包？
   建议：是；社区不可信插件不进入首发。

3. MCP 首发是否只开放只读连接？
   建议：默认是；写入场景逐个评审并要求 Ticket 与人工确认。

4. 团队共享工作台是否进入首发？
   建议：首发只做私有与官方方案复制；团队只读共享进入 P1。

5. 谁对可执行插件安全认证拥有最终决策权？
   建议：平台安全/架构评审人拥有 A，平台治理负责人保留平台准入 A。

6. 哪些动作必须人工确认？
   建议：业务系统写入、外部发送/发布、权限扩大、关键审批和不可逆动作。

7. 首发允许哪些治理例外？
   建议：仅允许元数据、兼容或业务分类例外；安全底线、权限隐瞒和票据绕过不允许例外。

8. 资源下架后如何保障已有用户？
   建议：保留实例和配置，显示只读占位，运行中任务按风险决定中止或允许完成。

9. 治理控制台首发做到什么程度？
   建议：可查资源、Owner、版本、认证、运行和风险，可执行禁用、回滚和审计查询即可。

10. 认证团队何时进入？
    建议：P0 稳定且审核 SLA、例外和事件处置跑通后，再小范围试点。

## 15. 上线验收清单

### 15.1 Scope 与责任

- [ ] 平台治理定义已评审，不包含业务正确性和数据内容主责。
- [ ] Skill、MCP、面板插件、工作台方案均纳入资源清单。
- [ ] 每类资源有明确 Owner、发布者、认证人和处置人。
- [ ] Function Owner 与平台治理负责人的决策边界已确认。

### 15.2 供给

- [ ] 所有首发资源有稳定 ID、版本、来源和权限说明。
- [ ] 所有可执行插件完成安全审核和兼容测试。
- [ ] Skill 文档包含适用场景、输入输出、限制和支持渠道。
- [ ] MCP Tool 已完成读写副作用分类。
- [ ] 敏感配置和明文密钥扫描已接入发布、共享和复制流程。

### 15.3 权限

- [ ] 三层权限取交集已在服务端实现。
- [ ] 安装与可见不会扩大业务数据权限。
- [ ] 工作台复制不携带原 Owner 私有配置。
- [ ] 管理员治理权限不能读取未授权业务数据。

### 15.4 运行

- [ ] AI Principal 与 Runtime Profile 强绑定。
- [ ] Action Ticket 绑定上下文、动作和有效期。
- [ ] 工具 allow/deny、预算、并发和超时生效。
- [ ] 高风险动作有人工确认。
- [ ] Run、Ticket、Grant 和资源版本可关联。

### 15.5 处置

- [ ] 资源可暂停、禁用、恢复和下架。
- [ ] 插件禁用后显示占位，不删除用户配置。
- [ ] 票据可吊销，运行可中止。
- [ ] Run 停止、资源禁用、票据吊销和回滚时限经过演练。
- [ ] S1/S2/S3 事件处置手册已演练。

### 15.6 审计与指标

- [ ] 发布、安装、连接、授权、执行、失败和禁用均记录审计。
- [ ] 审计不包含 token、凭据和完整敏感配置。
- [ ] 应治理资源和高风险动作的覆盖率可计算。
- [ ] 治理证据完整率和审计还原通过率可计算。
- [ ] 治理逃逸率有明确抽检方法和样本量。
- [ ] 运行中止、资源禁用和回滚恢复时长可观测。
- [ ] 治理审核 SLA 和例外合规率可计算。
- [ ] 治理指标有明确 Owner、数据源和复盘节奏。

## 16. 结论

上线初期治理的关键不是“把平台所有事项都纳入审批”，而是建立一条可验证的控制链：

> **资源可识别 -> 来源可认证 -> 权限可解释 -> 执行可限制 -> 行为可审计 -> 风险可止损。**

首发阶段优先完成受控供给、三层权限、运行票据、预算、审计、禁用和回滚。只有当这些基础稳定后，才逐步开放认证团队、私有市场和自动审核。

治理既不负责把平台业务做大，也不负责把页面做快。它的最终目标是：让平台内的资源和高风险动作都在明确边界内运行，并且一旦越界，能够被及时发现、停止、追溯和处置。
