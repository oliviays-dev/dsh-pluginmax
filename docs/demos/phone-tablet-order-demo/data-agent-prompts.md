# Data Agent 演示提示词

> 适用版本：2026-11-03
> 演示账号：周宁
> 数据集：`orders-facts`
> 数据模式：`demo`，非生产

## 设计原则

代码块中的内容是录制时真实发送给 Data Agent 的业务问法。用户只说业务问题、时间范围、
权限要求和决策目标，不预先罗列 `QueryRun`、`dataCutoffAt`、`permissionSummary`、
工具名或指标版本。

工具发现、权限说明、数据截止、指标版本和 QueryRun 由 Agent 根据平台规则主动补齐，
再作为录制验收点检查。

本场景只进行两轮 Data Agent 对话：

1. 判断今天华东手机/平板订单异常规模和构成；
2. 拆解渠道、金额影响和处置方向，并给出人机任务分工。

回执回来后不再让 Data Agent 生成正式报告。周宁把同一 QueryRun 证据、
李工回执和 WMS 回执带入与 `周宁的AI小助理` 的一对一沟通，由 CodeBuddy
生成管理报告 HTML。

## 1. 计划员初步问询

### 用户实际输入

```text
林岚刚问我，今天华东手机平板的订单异常怎么突然高了。你帮我快速看一下，先给个简短结论，不用出正式报告。

今天一共多少单、异常多少单，主要是支付失败、取消还是履约超时？这三类按单数从高到低列一下，
各自占异常量多少。这里只讲订单构成，先别把构成直接说成业务原因。

数据截止到什么时候、和今天查询到的时间差多少，也说明一下，截止之后没进来的订单别当成已经纳入。
口径和来源一起说一下，顺便确认是不是演示数据。我的权限范围按实际讲，没覆盖的区域别当成零。
订单数据看不出来的原因别往 SKU、序列号或仓库作业上猜，标成需要人工核实就行。
```

### 录制验收点

- Agent 实际调用只读数据工具，并说明发现的数据集和认证指标；
- 返回订单量 1,658、异常量 126、异常率 7.6%；
- 返回支付失败 52、取消 31、履约超时 43；
- 三类异常按单数降序表达：支付失败 52 > 履约超时 43 > 取消 31，并给出 41.3% / 34.1% / 24.6%；
- 不把“构成占比”写成已经证实的业务“原因”；
- 返回真实 QueryRun ID、指标版本和 `dataCutoffAt`；
- 正确解释周宁当前 Member 权限，不把未覆盖区域按 0 处理；
- 若查询入参晚于 `dataCutoffAt`，明确说明截止后的时段未纳入；
- 明确“演示数据、非生产”；
- 区分订单事实和待人工核实原因，不推断 SKU、IMEI/SN 或仓配作业状态。

### 预期 brief

```markdown
截止本次查询时，今天华东数码订单 1,658 单，订单异常 126 单，异常率 7.6%。

- 支付失败：52 单，占异常量 41.3%
- 履约超时：43 单，占异常量 34.1%
- 取消：31 单，占异常量 24.6%

口径：订单异常 v1 = 支付失败 + 取消 + 履约超时，按订单去重；不含退款和金额异常。
数据：orders-facts，演示数据，非生产。
权限：当前账号的 Member 策略覆盖华东、华南；华北、西南未覆盖，不能推断为零异常。
时间：查询入参为今天 00:00 至查询时刻；实际数据快照截止 dataCutoffAt。
若查询时刻晚于该截止时间，两者之间的订单未纳入本次结果。
证据：本次查询的 QueryRun、dataCutoffAt、指标版本和权限摘要见下方证据区。

初步看，异常构成主要来自支付失败和履约超时，但订单数据只能说明构成，
不能证明支付渠道、库存、仓配作业等具体原因；也不能确认具体 SKU、IMEI/SN、库存或成品仓状态。
```

### 录制时记录

从本次真实输出抄录后续任务和报告需要的事实：

```text
QueryRun ID：{{实际值}}
dataCutoffAt：{{实际值}}
permissionSummary：{{原样}}
指标版本：{{实际值}}
```

### 讲解文案

> 周宁问的是“异常是不是有点高”，而不是在填一张数据字段表。Data Agent 需要自己找到授权数据，
> 判断口径，并把结论、数据截止时间、权限和查询记录一起带回来。订单域仍然只读，
> 也不会把订单字段猜成库存原因。

## 2. 计划员继续深入

### 用户实际输入

```text
顺着刚才这个结果往下拆一下。支付失败、取消和超时分别落在哪些渠道、商家和支付方式上？
按订单金额看，大概影响多大？权限外的明细不要展示。

然后帮我分一下处置方向：哪些可以先做支付重试，哪些需要成品仓核实，哪些走退款、取消或改约。
订单数据能证明到什么程度就说到什么程度，需要人工确认的原因单独列出来。

最后给我一个执行分工建议：人工这边需要谁去核什么，履约 AI 伙伴接哪一个三级任务；
回执和 WMS 结果回来以后，我在一对一沟通里让 AI 小助理整理管理报告。
时间和口径沿用刚才，不要再换一套。
```

### 录制验收点

- 沿用第一轮时间范围、异常口径、QueryRun 和权限；
- 按支付方式、渠道、商家和订单状态拆分；
- 金额影响有来源，不展示权限外订单明细；
- 分开订单事实与待人工核实原因；
- 给出支付恢复、成品仓再平衡、退款/取消/改约三类处置方向；
- 人工任务建议给李工，唯一 AI 三级任务建议给履约 AI 伙伴；
- 小助理作为第二个业务 AI 伙伴，只在一对一沟通中制作管理报告，不创建 C 任务；
- 不重新解释“异常”口径，不生成正式报告。

### 预期回答

```markdown
异常仍是 126 单、7.6%，时间范围、权限和口径与上一轮一致。

从订单数据看，支付失败和履约超时是当前最需要分别处理的两类：

1. 支付失败：先看支付方式、渠道和订单保留时间，判断哪些可以重试或换支付方式恢复。
2. 履约超时：需要李工核实受影响 SKU、IMEI/SN、成品仓可分配库存、出库能力和跨仓调拨条件。
3. 取消：需要订单运营核实客户主动取消、库存占用超时和促销价格问题。

建议创建两个执行任务：

- `[PT-ORD-001-A] 核实成品仓 SKU/序列号与跨仓履约`
  - 负责人：李工（ligong）
  - 描述：核实华东受影响订单对应 SKU 的可分配库存、IMEI/SN 状态、出库能力、
    跨仓库存归属变更、高货值运输交接和签收要求；给出可再平衡范围、不可履约原因和仓配约束。
- `[PT-ORD-001-B] 生成成品仓订单再平衡工单`
  - 负责人：履约 AI 伙伴
  - 描述：华东手机/平板订单异常处置已进入仓配执行阶段。李工已确认 37 单可从
    华东备用成品仓调拨至华东履约仓，预计金额 ¥194,125，需在当天 17:00 前完成
    库存锁定、库存归属变更和订单改派。请编制可提交仓配执行的工单草稿，写清
    订单范围、仓库、交接时点及 SKU、IMEI/SN、保价运输、身份核验签收和发票售后要求。

回执和 MCP 建单结果齐了以后，再由周宁在 AI伙伴 1:1 沟通中请 AI 小助理生成 HTML 管理报告。
小助理不接任务，不重新查数据，也不持有业务写工具。
```

### 讲解文案

> 这一步像计划员继续追问：哪些原因能靠订单数据分清，哪些必须找仓配确认，以及后面该怎么分工。
> Data Agent 仍然只读，但把分析推进成了可执行任务。管理报告由另一个外部运行时伙伴在 1:1 中完成，
> 不是再开一个任务让 Data Agent 写。

## 3. 业务回执与报告证据交接

李工提交回执、周宁完成人工确认、WMS MCP 返回工单后，不再发给 Data Agent 生成正式报告。
把以下证据原样带入 `周宁的AI小助理` 的一对一沟通：

```text
Data Agent：
- QueryRun ID：{{真实值}}
- dataCutoffAt：{{真实值}}
- permissionSummary：{{原样}}
- 订单量 1,658、异常 126、异常率 7.6%
- 支付失败 52、履约超时 43、取消 31

李工人工回执：
{{粘贴真实任务回执}}

业务动作：
- Action Ticket：AT-PT-ORD-001-B
- 人工确认人：周宁
- MCP tools/call：wms_rebalance_work_order_create
- 业务工单：WO-RB-DEMO-1030-017
- 幂等键：PT-ORD-001-B
- 再平衡 37 单，预计订单金额 ¥194,125

结果对账：
- 126 = 83 恢复履约 + 43 退款/取消/改约
- 83 = 46 支付恢复 + 37 成品仓再平衡
```

1:1 实际发送内容见 [ai-assistant-prompt.md](./ai-assistant-prompt.md)。

### 证据验收点

- 1:1 消息中的 QueryRun 与白天 Data Agent 输出一致；
- `dataCutoffAt`、权限摘要和指标版本没有被改写；
- 李工回执明确标为人工提供；
- Action Ticket、工单号、37 单和幂等结果来自真实页面与 MCP 回执；
- 小助理不声称重新查询 Data Agent、OMS 或 WMS；
- 报告附件真实出现在 1:1 对话中，而不是只返回文件路径。

### 讲解文案

> 证据不是靠系统“猜着关联”的。周宁把已经核对过的 QueryRun、人工回执和 MCP 回执一起交给小助理，
> 所以报告能写清楚哪些来自只读数据、哪些来自人工核实、哪些来自受控业务动作。

## 4. Data Agent 失败时的自然追问

如果 Agent 没有展示查询记录：

```text
结论我看到了，但还缺这次查询的来源和数据截止时间。把查询记录、权限范围和口径也补一下，
没有实际执行的部分不要补造。
```

如果第二轮又执行了一次不必要的新查询：

```text
这一轮沿用刚才那份结果就行，不要重新换一套数据。如果引用不到上一条成功查询，
说明哪里断了，别用新数字接着分析。
```
