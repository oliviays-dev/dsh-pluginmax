## 2. 目标与边界

### 2.1 目标

将任务详情重构为双栏工作区：

- 左栏承载以任务派发消息起始的会话流和统一输入区；任务详情不再重复展示 Runtime 区。
- 右栏承载任务标题、状态、描述、状态操作和固定四页签。
- 桌面端独立滚动，窄窗口和移动端顺序堆叠，不产生页面级横向溢出。

### 2.2 只修改

- `plugins/dsh-collab-task/client/index.js` 中任务详情专属 React 组件、渲染逻辑和 `.pmtask-detail-*` / `.pmtask-*` 作用域样式。
- `plugins/dsh-collab-task/src/client-smoke.test.ts` 中任务详情相关测试。
- 本文档和必要的详情页测试记录。

### 2.3 不修改

- 任务看板、卡片、筛选、搜索、排序。
- 任务创建页、任务编辑弹窗。
- 项目、会议、AI伙伴、工作流、工作台及平台导航。
- 后台路由、服务、数据模型、权限守卫。
- AI伙伴上下文拼装、记忆注入、消息投递、Run 创建和执行分发。
- 共享公共组件和全局样式。

### 2.4 组件和文件改动边界

为避免改变客户端模块加载和构建协议，本次没有新增运行时依赖，也没有改动插件入口或请求协议。详情改造仍集中在 `client/index.js`：

- `TaskDetail`：负责详情数据加载、页签状态、编辑状态和任务动作入口。
- `TaskContentEditForm`：顶部摘要区的轻量编辑表单，只暴露标题和描述。
- `BasicInfoEditForm`：基础信息页签的独立编辑表单，负责负责人、优先级、截止时间、Review 配置、执行策略和运行参数。
- `taskRuntimeView`：只读推导当前运行时、模型和推理强度展示值。
- 既有 AI执行记录、产出文档、任务动态区块保持原数据来源和联动逻辑。

新增样式均限制在 `.pmtask-detail-page`、`.pmtask-detail-*` 或 `.pmtask-basic-*` 作用域内，不改任务看板、创建弹窗或平台级公共组件。

## 3. 信息架构

### 3.1 桌面布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 返回 / 任务编号 / 关注 / 当前状态                           │
├───────────────────────────────────┬──────────────────────────┤
│ 返回 / 项目 / 关注                 │ 标题 / 状态 / 描述       │
│                                   │ 状态操作按钮             │
│ 会话滚动区                        │ 基础信息 | AI执行记录    │
│ - 任务派发消息                    │ 产出文档 | 任务动态      │
│ - 历史消息 / 评论 / 系统消息      │                          │
│                                   │ 当前页签内容             │
│ 输入区                            │                          │
└───────────────────────────────────┴──────────────────────────┘
```

- 左栏建议 `minmax(0, 1.35fr)`，右栏建议 `minmax(360px, .92fr)`。
- 详情根节点使用 `min-width: 0`、`min-height: 0`；左右栏各自滚动。
- 右栏标题和页签保持固定，仅页签内容滚动。
- 宽度不超过 `900px` 时改为单栏：先显示任务摘要与状态，再显示会话；右栏页签不断裂。
- 宽度不超过 `640px` 时输入工具与操作按钮换行，仍不得覆盖输入框或内容。

### 3.2 左栏

- 会话流第一项为创建人在派发时刻发出的普通任务描述消息，使用创建人、创建时间和常规消息气泡，不增加“任务要求”卡片、Runtime Dock 或专属交互样式。
- 不显示“参与人”头部、不显示“任务对话”标题、不显示独立“执行历史”标题。
- 会话之后为统一输入区；滚动区与输入区分离。

### 3.3 右栏

- 顶部直接展示任务标题、状态、描述，不出现“任务描述”标题。
- 状态操作按钮位于描述下方。
- 顶部编辑入口只编辑标题和描述，并在右栏原位替换摘要内容；进入该状态后隐藏下方页签，不推动页签位置，也不替换左栏会话。
- 点击顶部编辑入口时只展示标题、描述及取消/保存操作，不混入项目、优先级、验收标准、执行策略等基础信息字段。
- 页签固定为：基础信息、AI执行记录、产出文档、任务动态。
- 基础信息展示：负责人、归属项目、任务类型、优先级、截止时间、创建人、完成后自动提交 Review、Review 自动通过、执行运行时、模型 / 推理强度、执行策略。任务状态只在顶部摘要展示，不在基础信息重复。
- 基础信息只在该页签内进入编辑态，其他页签仍可正常切换；负责人切换只在基础信息编辑态提供。
- 基础信息编辑入口位于内容区右下方，保存按钮文案统一为“保存”；编辑态左右保留页面级留白。
- 基础信息采用双列铺满布局，除执行策略跨两列外，其余字段成对排列，不保留空单元格。
- 验收项不拼入任务派发消息，也不重复出现在基础信息；任务记录中的验收数据保持不变。
- 关联会议/工作流不新增右侧区块；工作流入口由状态操作和现有链接动作承载。

## 4. 状态、按钮、权限与数据来源矩阵

### 4.1 主状态和正交状态

- 主状态：`todo / progress / review / done / cancelled`。
- 正交状态：`archivedAt`、`queueState`、`needsInput`、Run 状态。
- 不新增主状态，不改变已有事件产生逻辑。

### 4.2 状态操作按钮

按钮统一使用图标 + 文案，固定高度、圆角和间距。样式语义：

- `primary`：开始、认领、提交验收、通过、复原。
- `caution`：退回、退回审批。
- `danger`：取消任务。
- `neutral`：催办、归档、打开工作流节点。

| 场景 | 显示按钮 | 前端显示条件 | 数据/接口来源 |
| --- | --- | --- | --- |
| 已归档 | 复原 | `archivedAt` 有值 | Task 记录；`/tasks/action restore` |
| 工作流任务 | 打开工作流节点 | `task.workflow` 有值 | Task 记录；现有导航事件 |
| 工作流审批 | 通过审批、退回审批 | `approvalPolicy` 有值、`status=review`、`canReview=true` | `reviewableTaskIds`；`/tasks/action approve|reject` |
| 人类 `todo` | 开始 | `receiverType=human`、`status=todo`、归属当前用户 | Task 记录；`/tasks/action start` |
| 角色 `todo` | 认领 | `receiverType=role`、`status=todo`、当前用户在角色成员目录中 | `taskBelongsTo` 角色口径；`/tasks/claim` |
| AI `todo` | 不显示人工开始 | `receiverType=agent` | 不调用开始接口 |
| `progress` | 提交验收 | 归属当前用户、非审批任务 | `/tasks/action submit` |
| `progress` / `review` | 取消任务 | 创建人、任务未归档且非终态 | 见 11.1 待确认项 D1 |
| `review` | 通过、退回 | `canReview=true`；退回必须填写说明 | `/tasks/action approve|reject` |
| 人类任务非终态 | 催办 | 当前用户为创建人、负责人不是自己 | `/tasks/action nudge` |
| `done` / `cancelled` | 归档 | 未归档 | `/tasks/action archive` |

约束：

- 前端只控制入口展示；服务端仍是最终权限与状态校验来源。
- 不修改现有 `canReviewTask`、`requireOpen`、`requireActive` 或任务动作映射。
- 工作流任务不显示普通 `start/submit/cancel`；审批结论仅在待审批 Review 态出现。

### 4.3 默认页签

| 负责人类型 | 默认页签 |
| --- | --- |
| `agent` | AI执行记录 |
| `human` | 基础信息 |
| `role` | 基础信息 |
| `unassigned` | 基础信息 |
| 工作流任意负责人 | 基础信息；审批任务仍按负责类型规则，不强制跳 AI执行记录 |

页签仅在切换任务 ID 时重新初始化；同一任务状态刷新不重置用户当前页签。

### 4.4 数据来源

| 区域 | 数据来源 | 是否新增接口 |
| --- | --- | --- |
| 任务标题/状态/描述/基础信息 | `TaskRecord` props | 否 |
| 消息、评论、回复、动态 | `task.messages`、`task.comments`、`task.events` | 否 |
| Run 列表和轮次 | `task.agentRunIds` + `/agent/runs` | 否 |
| 当前 Run 详情 | `/agent/runs/detail` + `/agent/execution/detail` | 否 |
| 执行计划/步骤/事件/授权 | `executionControl.plan/events/gates` | 否 |
| 产出文档 | `/tasks/documents` | 否 |
| 负责目录与角色成员 | `directory` props | 否 |
| 当前用户与验收权限 | `currentUser`、`reviewableTaskIds` | 否 |

## 5. 左栏会话设计

### 5.1 会话内容

- 起始节点为任务派发消息，包含任务描述、创建人和创建时间，并完全复用普通消息的左右对齐、头像和气泡规则。
- 历史内容按时间排序，包含现有任务消息、评论和评论回复。
- `task.events` 继续只在“任务动态”页展示，不复制进会话，避免状态事件与对话重复。
- 内容正文继续使用现有 Markdown 渲染；附件沿用现有展示方式。

### 5.2 对齐与气泡

- 当前用户发送的 `kind=human` 消息：靠右，显示名为“我”。
- 其他人员、Agent、系统消息：靠左。
- 系统消息使用低强调样式，不放右侧。
- 对话样式与沟通会议一致：
  - 头像与正文横向排列；
  - 自己的消息头像在右；
  - 桌面正文最大宽度约 `72%`，移动端约 `82%`；
  - 他人气泡圆角 `3px 8px 8px 8px`；
  - 自己气泡圆角 `8px 3px 8px 8px`，使用蓝色弱底和蓝色边框。
- 不修改会议模块样式，只复制视觉规则到 `.pmtask-detail-conversation` 作用域。

### 5.3 最新定位与滚动保持

- 首次打开任务详情时，在会话内容渲染后的下一帧滚动到底部。
- 新消息到达时，仅当用户原本位于底部附近时自动跟随；用户主动上翻后不强制跳转。
- 右侧页签切换不重新挂载左栏，不改变 `conversationScrollRef.current.scrollTop`。
- 任务 ID 变化时重置滚动状态并重新定位到新任务最新消息。

## 6. 输入区设计

- 只保留一个输入区，通过紧凑的 `讨论 / 指令` 意图区分发送语义。
- `讨论`调用现有 `/tasks/comment`，默认仅记录，不触发执行。
- `指令`调用现有 `/tasks/message`，由任务负责人和已有分发链路决定是否触发 Run。
- 发送按钮统一为“发送”；按钮旁仅保留常规字重后果说明：
  - 讨论：`仅记录讨论，不进入本次执行上下文`
  - AI 负责人：`将触发一次 Agent Run，并同步之前关键共识`
  - 人类负责人：`将通知负责人，并同步之前关键共识`
- 不新增整行 To/结果责任说明。
- `@` 用于通知人员或 AI伙伴；不在输入区下方常驻同步对象行。
- `关键共识`保留为讨论后的独立标记，不把普通讨论自动提升为执行要求。
- 自己消息靠右，附件随气泡对齐。

## 7. 消息标签

- 任务派发：`指令 · 驱动执行`
- Agent 回复：`执行反馈`
- 普通评论/回复：`讨论 · 仅记录`
- 已标记共识：`关键共识 · 下轮同步`
- 系统消息：`系统`

## 8. 右侧页签

### 8.1 基础信息

显示：

1. 负责人
2. 归属项目
3. 任务类型
4. 优先级
5. 截止时间
6. 创建人
7. 完成后自动提交 Review
8. Review 自动通过
9. 执行运行时（只读）
10. 模型 / 推理强度
11. 执行策略

基础信息编辑态支持：

- 负责人切换，选择器按“人员 / AI伙伴 / 角色”分组；
- 优先级、截止时间；
- 完成后自动提交 Review、Review 自动通过；
- 公开网页、工具确认、工具事件三类执行策略；
- 运行时、模型、推理强度的来源说明。

归属项目、任务类型、创建人保持只读；任务状态只由顶部状态与状态机操作承载。审批工作流必须由人工给出结论，因此“Review 自动通过”在该场景只读。前端编辑态只控制可操作入口，保存仍复用既有任务更新、改派和 Review 配置接口。

执行运行时、本轮模型和推理强度的读取顺序：

1. 当前选中 Run 的 `execution.runtime`、`execution.model`、`execution.reasoningEffort`。
2. 任务 `executionPolicy.runtime` 中的任务级选择。
3. 责任 AI伙伴绑定的外部 Runtime 及 Runtime 默认模型。
4. 上述数据都不存在时显示“未采集”，不再用“未指派 AI伙伴”暗示任务没有执行者。

只读态把模型和推理强度合并为一个字段，例如“deepseek-v4 · 高”。没有任务级显式选择时，继承模型显示为“模型名（默认）”，推理强度显示“低 / 中 / 高”等产品文案并追加“（默认）”。编辑态仍保留模型、强度两个独立配置控件。

### 8.1.1 执行策略说明

执行策略回答的是“这一轮任务允许 Agent 使用什么来源、哪些工具需要人工确认、是否必须留下可审计的工具事件”：

- `公开网页`：是否允许访问公开网页和监管文件。开启后，事实性结论需要记录来源、发布日期和访问时间。
- `工具确认`：写文件、执行命令、外部发布等动作是否需要人工确认。
- `工具事件`：是否要求记录实际发生的工具调用，作为后续审计和复盘的证据。

展示值来自 `TaskRecord.executionPolicy`：

- 公开网页：`sourcePolicy.allow` 是否包含 `public-web` / `regulatory-filing`。
- 工具确认：`toolPolicy.requireApproval` 是否非空。
- 工具事件：`evidence.requireToolEvents`。

修改入口：

- 已创建任务：任务详情 → 基础信息 → 编辑 → 执行策略 → 保存。
- 新建任务：新建任务弹窗中的执行策略区域。
- 执行运行时、模型和推理强度：优先来自任务执行策略；未指定时由责任 AI伙伴实例配置和其绑定的外部 Runtime 决定。AI伙伴/Runtime 绑定应在 AI伙伴配置中修改。

执行策略变更影响后续 Run；已经形成的 Run 使用其创建时的快照，不会被回写。若 Runtime 为“仅执行后观察”（`observe-only`），即使开启工具确认，Runtime 也只能记录已执行动作，无法事前阻断；界面不能把它描述成已经成功拦截。

不显示最新进展、验收项、关联事项等重复内容。

### 8.2 AI执行记录

- 完全沿用现有结构、文案、轮次菜单元数据、执行计划、产出物、执行过程、运行信息、授权和空态。
- 仅从原右栏纵向区块迁移到页签容器。
- 不改 Run 轮次选择、轮次指令展开、执行授权决定或详情轮询逻辑。
- “Agent 执行计划”标题不再展示“摘要 / 根据事件整理”等来源角标，也不重复渲染由事件生成的过程摘要句。
- `observe-only` 的边界说明使用普通文本，不增加高亮容器；等待人工授权的真实 Gate 仍保留现有操作框。

### 8.2.1 工作流节点讨论

- 工作流任务的输入区只保留“讨论”，不再展示“指令”切换。
- 对负责人为 Agent 的工作流任务，讨论复用现有协作消息链路，并以 `assist + workflow-discussion` 运行。
- 讨论目标既可以用 AI伙伴实例 ID，也可以用已绑定的员工身份 ID 解析，避免工作流投影任务把生效伙伴误报为不存在。
- 后端上下文明确限制：Agent 可以分析方案、判断风险、帮助准备材料和交付物草稿；不得推进工作流、提交审批或提交最终交付物。
- 讨论 Run 不调用工作流提交或审批动作，不改变任务主状态和 `workflow.outcome`。
- Agent 回复仍使用“执行反馈”标签，不新增“节点分析”标签。
- 工作流节点初始消息使用“工作流 · 节点任务”，用户讨论使用蓝色“讨论”标签。
- 审批、附件上传和最终交付物提交继续通过右侧操作或工作流页面完成。

### 8.3 产出文档

- 数据只来自 `/api/collab/tasks/documents` 返回的现有 Run 文档。
- 同名文档按 `name` 去重，保留 `updatedAt` 最新版本；无时间时保留现有列表顺序中的首个。
- 每项展示：
  - 产出人或 Agent 名称；
  - AI 标识（产出者类型为 Agent 时）；
  - 更新时间；
  - Run ID；
  - 对应交互轮次。
- 下载复用现有 `downloadDocument`；不可用文档禁用并解释原因。
- 没有文档时显示“当前任务还没有产出文档”。

### 8.4 任务动态

- 继续展示 `task.events` 现有事件，不在前端生成事件。
- 默认倒序显示，保留完整消息和时间。
- 无事件时显示空态，不改事件产生、排序和存储。

## 9. 异常与空状态

| 场景 | 展示 |
| --- | --- |
| 无 Run | 左栏不展示 Runtime 信息；AI执行记录显示“暂无执行记录” |
| Run 列表可用但详情失败 | 保留历史消息和 Run 列表，显示“详情加载失败”及重试提示 |
| 当前 Run 无执行计划 | 仅在 AI执行记录页显示“当前 Run 尚未产生执行计划” |
| 等待补充但无问题正文 | 显示通用“Agent 等待补充信息”提示，不伪造问题 |
| 无文档 / 工作区不可用 | 分别显示无产出文档、任务工作区不可用 |
| 文档版本重复 | 只展示最新版并提示合并数量 |
| 无任务动态 | 显示无动态空态 |
| 已归档 / 已取消 | 输入与状态动作锁定；只保留复原或归档等合法操作 |
| 负责人角色失效 | 保留现有改派提示，发送按钮禁用 |
| 窄窗口 / 移动端 | 单栏堆叠，正文、按钮、同步 chip 均换行，不遮挡 |

## 10. 样式隔离方案

- 所有新增选择器必须位于 `.pmtask-detail-page` 或 `.pmtask-detail-*` 根节点下。
- 不新增全局标签选择器，不修改现有看板 `.pmtask-card`、筛选 `.pmtask-filter`、创建弹窗 `.pmtask-modal`。
- 不修改其他插件和 shell 样式。
- 在详情根节点定义自己的 CSS 变量或直接使用 `--dsw-alias-*` 主题变量。
- 桌面、容器窄宽度和移动端均使用 `min-width: 0`、`overflow-wrap:anywhere`、`max-width:100%` 防止横向溢出。
- 媒体查询只作用于 `.pmtask-detail-page` 内部。

## 11. 已确认决策

### D1. 普通任务“取消”写接口（已确认）

当前后端没有 `/tasks/action` 的 `cancel` 分支；普通任务只能通过现有 `/tasks/status` 写为 `cancelled`，但该接口本身没有创建人/管理员限制。由于本次禁止修改后台权限和状态守卫，建议：

- 前端仅在创建人、平台管理员且任务非终态时展示“取消任务”；
- 使用现有 `/tasks/status` 提交 `{taskId,status:"cancelled"}`；
- 将服务端权限缺口记录为后续治理项，不在本次修改。

如果要求“取消”也必须具备服务端动作级权限，则本次必须先放开后台范围或暂不交付取消按钮。

### D2. Follow-up 快捷回答来源（已由后续设计移除）

后续交互确认不在任务详情左栏展示 Runtime Follow-up 区。本次不扩展 `waiting_input` 数据结构。

### D3. 评论是否合并进会话流（已确认）

参考稿将会话消息与评论合并按时间展示。建议按参考稿合并，任务动态仍独立展示系统事件。

## 12. 测试方案

### 12.1 单元与契约测试

- 人类 `todo`：显示开始，不显示认领；默认基础信息。
- 角色 `todo`：角色成员显示认领，非成员不显示；默认基础信息。
- AI `todo`：不显示人工开始；默认 AI执行记录。
- 工作流任务：显示打开工作流节点；仅审批 Review 显示通过/退回；不显示普通状态按钮。
- `progress / review / done / cancelled / archived` 按钮矩阵和设计一致。
- 当前用户消息靠右且显示“我”；其他 human/agent/system 靠左。
- 会话起始节点为任务派发消息，无参与人头部、独立“任务要求”卡片和“任务对话”标题。
- 默认滚动到最新消息；切换右侧页签后滚动位置不变。
- 输入区使用单一编辑器承载讨论/指令意图，不增加整行 To/结果责任说明。
- 提及同步支持问询/周知/协作，发送 payload 不增加 `intent`。
- 顶部编辑只包含标题和描述；进入后隐藏页签且不改变左栏会话。
- 基础信息编辑只改当前页签，负责人选择器按人员 / AI伙伴 / 角色分组。
- 基础信息展示 Review 配置、运行时、模型、推理强度，并保持双列无空单元格。
- AI执行记录中的计划、当前步骤、进度和队列元数据只读取当前选中 Run。
- 轮次切换后 AI执行记录、执行计划和轮次指令联动。
- 文档同名去重、版本、时间、Run、轮次与下载。
- 任务动态沿用现有事件。
