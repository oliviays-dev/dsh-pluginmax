## 1. 结论先行

Data Agent 不能只在用户显式分享卡片时工作。对于“今天有没有订单异常”“本月华东区退款率怎么样”这类 general 数据问题，系统必须能够：

1. 按当前用户、工作区、项目和 Runtime Profile 解析可访问数据范围；
2. 搜索数据集、认证指标和可用维度；
3. 在低风险、高置信场景下使用明确默认值直接查询并输出 brief；
4. 在口径冲突、范围受限或查询成本过高时才向用户澄清；
5. 始终通过服务端只读查询工具执行，不允许模型自由访问数据库；
6. 返回数据截止时间、覆盖范围、口径、查询证据和缺失信息；
7. 不把“用户有权访问订单数据”错误理解为“用户可查询全部订单”，行级和列级策略仍由服务端执行。

首版采用：

- **订单域先行**；
- **认证指标 + 参数化聚合查询**；
- **默认授权范围快速 brief，必要时澄清**；
- **不开放自由 SQL**。

## 2. 背景与问题

当前 Data Agent 的上下文来源以“用户选区”为中心。用户未分享卡片时，ContextPack 只包含会话、工作区、SOUL 和聊天历史，没有可查询的数据目录，也无法发现用户有权访问的指标或数据集。

因此用户问“今天有没有订单异常”时，Agent 只能回答“没有附带业务对象或数据源”，但平台实际上可能已经拥有该用户的订单数据授权。这会带来三个问题：

1. Data Agent 无法承担“常驻数据分析师”的默认能力；
2. 用户必须先知道数据在哪个页面、哪张卡片上，违背自然语言问询目标；
3. “数据权限”被错误简化成“是否选中了卡片”，而不是后端真实 ACL。

## 3. 目标与非目标

### 3.1 目标

1. 无选区时，Agent 可以根据自然语言发现并查询授权数据。
2. 简单、低风险问题优先直接给出数据 brief，不要求用户预先配置查询。
3. 存在关键歧义时，使用结构化澄清而不是开放式追问。
4. 查询、聚合、行级过滤和脱敏全部在服务端执行。
5. 结果可审计、可复现，并明确数据范围和数据截止时间。
6. 支持从 brief 继续下钻、生成报告、创建治理任务，但不自动执行写操作。
7. 保持对新增数据集、指标、连接器和 Agent 能力的扩展性。

### 3.2 非目标

本期不做：

1. 任意用户编写并执行自由 SQL；
2. 跨工作区拼接数据；
3. 自动修改生产业务数据；
4. 自动改变认证指标口径；
5. 无限制扫描全量明细数据；
6. 复杂的自主多 Agent 数据团队；
7. 预测、情景模拟和跨组织数据市场分析；
8. 所有数据域一次性接入。MVP 只要求订单域闭环。

## 4. 核心原则

1. **权限先行**：Agent 能看见什么、查询什么，由请求人、工作区、项目、数据集和 Runtime Profile 的交集决定。
2. **语义优先**：优先使用认证指标和语义模型，不直接生成自由 SQL。
3. **默认可用**：能安全推断的低风险问题先给结果，再说明默认口径。
4. **必要澄清**：只在结果可能因歧义产生实质差异时打断用户。
5. **证据可追溯**：每次结果必须带 QueryRun、数据截止时间、覆盖范围和口径版本。
6. **渐进加载**：先返回聚合摘要，用户要求时再下钻明细，不把全量数据送进模型上下文。
7. **无权限不降级**：没有数据授权时明确说明，不切换到其他组织或更宽松的数据域。

## 5. 用户与权限

| 角色 | 通用问询能力 | 管理能力 |
| --- | --- | --- |
| 业务成员 | 查询自己被授权的数据，保存个人报告 | 无数据连接和口径管理权 |
| 项目负责人 | 查询项目范围内授权数据，查看项目报告 | 配置项目级默认口径和优先级 |
| 工作区管理员 | 查询自身有权数据 | 配置工作区连接、默认范围、订阅和 Runtime |
| 数据管理员 | 查询自身有权数据 | 维护数据集、认证指标、维度、质量规则和授权策略 |
| 平台管理员 | 不因平台角色自动获得业务数据 | 维护系统 Agent 定义、连接器代码和平台级策略 |

有效数据权限：

```text
请求人的有效业务权限
∩ 工作区授权
∩ 项目 / 数据集授权
∩ 行级和列级策略
∩ Agent Runtime Profile 能力
∩ 连接器只读策略
```

平台管理员或 Data Agent 系统身份不能扩大请求人的数据权限。

## 6. 核心概念

| 概念 | 定义 |
| --- | --- |
| DataConnection | 一个受治理的只读数据连接，例如订单数据库只读副本、数仓或文件数据集 |
| Dataset | 可发现、可授权的数据集合，包含字段、时间字段、维度、粒度和新鲜度 |
| SemanticMetric | 认证指标，包含业务定义、计算公式、默认时间字段、可用维度和版本 |
| Dimension | 可分组维度，例如区域、品类、订单状态、支付方式 |
| DataPolicy | 工作区、项目、行级、列级、查询上限和脱敏规则 |
| QueryRun | 一次自然语言问询到查询结果的完整审计记录 |
| QueryResult | 经过权限过滤和聚合的结果，包含行数、口径、截止时间和 lineage |
| Data Brief | Data Agent 面向用户的默认摘要，不等同于正式报告 |

## 7. 典型场景

### 场景 A：宽泛问题直接给默认 brief

用户：“今天有没有订单异常？”

系统行为：

1. 解析为“订单异常”“今天”“当前工作区授权范围”。
2. 发现唯一高置信的订单数据集和认证异常指标。
3. 默认覆盖当前用户有权访问的全部订单。
4. 查询订单总量、异常量、异常率，并按状态、区域、品类拆分。
5. 先返回 brief，不阻塞追问。

输出示例：

```text
截至 10:30，今日可访问订单 12,840 单，异常 236 单（1.84%）。

- 支付失败 74 单
- 取消 58 单
- 履约超时 104 单
- 异常最多区域：华东（98 单）
- 异常最多品类：生鲜（63 单）

口径：订单异常 = 支付失败 + 取消 + 履约超时；覆盖当前工作区中你有权访问的订单；不含退款和人工标记异常。
```

随后提供：

- 按区域查看
- 按品类查看
- 查看异常订单样本
- 生成正式报告

### 场景 B：口径冲突时结构化澄清

用户：“看下今天的异常。”

系统发现“异常”可能指支付失败、退款、履约超时或金额异常，且不同口径会得出不同结论。

澄清卡：

```text
请选择本轮关注的异常范围

[ ] 支付失败
[ ] 取消
[ ] 履约超时
[ ] 退款
[ ] 金额异常

默认可先查看前三项
[按默认范围查看] [开始分析]
```

要求：

1. 只问一个关键问题；
2. 每个选项说明业务含义；
3. 提供推荐默认值；
4. 用户可以直接按默认值继续。

### 场景 C：权限范围受限

用户仅有权访问华东和华南订单，却问“全国今天订单异常”。

系统行为：

1. 不把无权限区域当作零；
2. 查询华东和华南结果；
3. 明确告诉用户未覆盖华北、西南等区域；
4. 提供“查看授权范围”或“联系管理员”的下一步。

### 场景 D：没有可用数据

系统提示：

1. 未找到当前工作区内可用的订单数据集；
2. 不伪造数字，不用示例值；
3. 提供“配置只读数据连接”或“将数据缺口转为治理任务”；
4. 有权限的管理员可以看到配置入口。

### 场景 E：从 brief 下钻

用户：“看华东生鲜。”

系统复用上一轮 QueryRun：

1. 保留原数据范围和口径；
2. 增加区域、品类过滤；
3. 重新查询并返回更小范围的 brief；
4. 不要求用户重复描述时间范围。

## 8. 交互设计

### 8.1 无选区问询

Data Agent 输入区保持正常聊天，不要求先选择卡片。

发送后展示以下进度：

```text
正在确认数据范围 → 正在选择认证指标 → 正在查询 → 正在汇总
```

不对用户暴露精确 SQL，但可以展示：

- 使用的数据集；
- 使用的指标和口径；
- 数据截止时间；
- 行级权限摘要；
- 查询是否被截断。

### 8.2 数据范围提示

对话结果顶部显示 scope chip：

```text
范围：当前工作区 · 华东/华南 · 你有权访问的订单
口径：订单异常 v1.2
截止：2026-10-30 10:30
```

用户可以点击查看范围详情。

### 8.3 Brief 结构

默认 brief 使用 Markdown：

1. 一句话结论；
2. 核心数字：总量、异常量、异常率；
3. Top 驱动：按状态、区域、品类；
4. 对比：昨日同期或近 7 天基线；
5. 数据口径与范围；
6. 数据缺口；
7. 建议下一步。

普通问询不自动输出完整报告章节。只有用户明确要求报告时才进入报告链路。

### 8.4 澄清规则

自动执行条件：

- 命中一个高置信认证数据集或指标；
- 默认时间、范围和口径可从工作区配置和用户问询确定；
- 查询只读且成本在限额内；
- 结果中能清楚说明假设。

必须澄清条件：

- 多个认证口径会产生实质不同结论；
- 用户权限只覆盖部分范围，默认全量可能误导；
- 查询成本超过阈值；
- 用户要求根因判断、对外报告或高风险决策；
- 无法确定业务实体是订单、退款还是售后；
- 没有可用数据，且问题无法降级为明确的数据缺口说明。

一次对话最多进行一轮主动澄清。用户回答后仍无法确定时，返回可用候选范围和限制说明。

## 9. 订单域 MVP 语义范围

### 9.1 订单数据集

首版订单数据集至少需要：

- 订单 ID；
- 下单时间；
- 支付时间；
- 订单状态；
- 支付状态；
- 区域；
- 品类；
- 商家或渠道；
- 承诺履约时间；
- 实际履约时间；
- 退款状态；
- 订单金额。

### 9.2 认证指标

MVP 认证指标：

| 指标 | 定义 |
| --- | --- |
| `order_count` | 指定时间范围内创建的订单数 |
| `paid_order_count` | 支付成功订单数 |
| `payment_failure_rate` | 支付失败订单 / 已结束支付尝试订单 |
| `cancel_rate` | 用户或系统取消订单 / 创建订单 |
| `fulfillment_timeout_rate` | 超过承诺履约时间仍未履约订单 / 应履约订单 |
| `order_exception_count` | MVP 默认异常口径：支付失败 + 取消 + 履约超时 |
| `order_exception_rate` | `order_exception_count / order_count` |

退款率和金额异常作为下一阶段认证指标，不混入 MVP 默认“订单异常”，避免总异常定义不可解释。

### 9.3 默认维度

- 区域
- 品类
- 订单状态
- 支付方式
- 渠道
- 商家

### 9.4 默认时间口径

- “今天”：工作区时区当天 00:00 至查询时刻；
- “昨天”：前一日完整自然日；
- 对比默认使用昨日同时间段；
- 趋势默认使用过去 7 天同一时刻基线；
- 时间字段默认为下单时间，履约异常使用履约时间。

## 10. 数据来源与结果可信度

1. 工作台现有静态指标属于演示数据，不得作为真实查询结果。
2. 真实查询必须返回 `dataCutoffAt` 和数据新鲜度。
3. 结果超过最大返回行数时，只返回聚合和截断说明。
4. 模型只看到服务端规范化后的聚合结果，不直接接触无权限原始行。
5. 任何失败都不得用假设值或示例数据补齐。
6. 同一指标定义版本变化后，应明确提示口径版本。

## 11. 安全、审计与动作边界

每次 QueryRun 至少记录：

- 请求人、Agent、工作区、项目；
- 自然语言问题；
- 数据连接、数据集、认证指标及其版本；
- 规范化时间范围和过滤条件；
- 行级策略版本和脱敏规则；
- 查询起止时间、耗时、返回行数；
- 是否截断、错误码和失败阶段；
- ContextPack、Agent Run 和结果引用。

写操作、外发、任务指派和权限变更仍必须经过动作票据或人工确认，不能由只读查询工具直接执行。

## 14. 验收标准

- [ ] 用户不分享卡片也可以问订单数据问题。
- [ ] Agent 能发现用户有权访问的订单数据集和认证指标。
- [ ] 宽泛问题在存在高置信默认口径时直接返回 brief。
- [ ] 口径冲突时展示结构化澄清和默认选项。
- [ ] 授权仅覆盖部分区域时，结果明确标出未覆盖区域。
- [ ] 查询结果包含范围、口径、数据截止时间和证据。
- [ ] 无数据或无权限时不显示猜测数字。
- [ ] 用户回答澄清后复用原会话、时间和范围。
- [ ] 生成正式报告需用户明确请求。
- [ ] 查询、数据范围、指标版本和审计信息可追溯。
- [ ] 自由 SQL、跨工作区查询和写数据库均不可达。
- [ ] Runtime Profile、模版、实例三层配置可独立维护且优先级明确。

## 15. 两步落地策略

本轮落地固定拆为两个阶段：

1. **产品相关模块的能力建设**：建设与订单无关的通用数据问询平台能力。
2. **订单 MVP**：通过订单领域适配验证真实业务闭环。

### 15.1 第一步：产品模块能力建设

目标是让平台具备“发现授权数据、解释数据、执行只读查询、返回证据”的通用能力，不绑定订单。

范围：

- Data Fabric 数据面；
- 只读数据连接与连接器 SPI；
- Dataset、Semantic Metric、Dimension 和 Data Policy；
- 用户可访问数据目录；
- QueryRun、QueryResult、权限摘要和证据；
- `catalog search / dataset describe / query explain / metric query / dataset query read-only` 工具；
- 无选区问询、默认 brief、结构化澄清、部分权限提示；
- Runtime、智能体模版、AI伙伴实例三层配置接入；
- 数据连接、数据集、指标和查询限额管理界面；
- 使用 Fake Connector 和 Fixture Dataset 的完整自动化测试。

第一阶段不包含：

- 订单业务口径；
- 订单物理表或订单专用 Prompt；
- 工作台真实经营指标迁移；
- 订单报告模板和订单 E2E 验收。

退出条件：

- 不依赖订单域，使用测试数据集即可完成“发现问题 → 澄清 → 查询 → brief”的闭环；
- 所有查询工具均为真实实现；
- 权限、RLS、列脱敏、查询限额和 QueryRun 审计完整；
- 无权限、无数据、超时和结果截断均能正确表达；
- 第二阶段接入订单域时，不需要修改 Data Agent 核心协议。

### 15.2 第二步：订单 MVP

目标是使用第一步的平台能力完成订单领域的真实数据问询和异常 brief。

范围：

- 订单只读 Connector 或内部订单数据适配器；
- 订单 Dataset、字段、时间字段和维度；
- 订单量、支付失败率、取消率、履约超时率、订单异常率；
- “今天有没有订单异常”“查看华东生鲜”等默认问询与下钻；
- 默认时区、时间范围、区域和权限范围；
- 订单 brief、证据展示、正式报告和 HTML 派生；
- 工作台真实订单指标逐步迁移到 Data Fabric；
- 真实账号、真实权限范围、真实查询的 GUI E2E。

第二阶段不包含：

- 重写 Data Agent 会话、Runtime 或权限系统；
- 为订单新增第二套 QueryRun 或工具框架；
- 绕过数据目录和认证指标直接执行自由 SQL；
- 在订单范围外扩展多个业务域。

退出条件：

- 用户不分享卡片，也能按真实权限回答订单异常；
- 宽泛问题默认返回范围、口径、截止时间和证据完整的 brief；
- 部分权限、口径冲突、成本超限和连接异常均能正确处理；
- 正式报告复用同一 QueryResult，不重新查询；
- 工作台真实指标与 Data Agent 查询结果使用同一指标定义。

### 15.3 阶段门禁

- 第一阶段未通过前，不接入订单真实数据。
- 第二阶段如果必须修改核心工具契约、ContextPack 结构或权限模型，视为第一阶段遗留缺口，应先补齐平台能力。
- 订单专用逻辑只能进入 Connector 配置、Dataset、Metric、Policy、Skill 和显示配置，不能散落到 Data Agent 通用代码。
- 两个阶段都必须保持只读、最小权限、可追溯和无自由 SQL。

## 16. 已确定的产品决策

1. MVP 首个真实数据域为订单。
2. 宽泛低风险问题默认给授权范围 brief，不强制澄清。
3. “订单异常”MVP 口径为支付失败、取消和履约超时。
4. 退款和金额异常在后续版本作为独立认证指标接入。
5. 首版不开放自由 SQL，只允许认证指标和参数化聚合查询。
6. 数据范围以请求人的真实权限为准，平台管理员和 Agent 身份不能扩权。
7. 只有用户明确要求时才生成正式报告，不把每个问答都升级为报告。
